Até aqui, o Passaporte só existia no seu computador. Agora ele ganha um endereço na internet, com HTTPS, que qualquer pessoa abre no celular. E a cada git push, a versão nova vai ao ar sozinha.

Esse é o Passaporte que o livro publicou no Render, a partir da etapa deste capítulo. Ao final, você vai saber publicar o seu: gerar o build, ligar o repositório do GitHub ao Render, entender por que um endereço como /passaporte pode dar erro 404 e escrever as regras que resolvem isso.

Num prédio comercial, o porteiro tem a lista das salas. Pergunte pela sala 302, e ele leva você até lá. Pergunte por "a reunião de vendas", e ele não acha nada na lista: "não existe". A reunião existe, mas acontece dentro de uma sala, e só quem está lá dentro sabe dela.

O servidor de um site estático é esse porteiro: só conhece arquivos. /passaporte não é um arquivo, é uma tela que o Angular monta dentro do app. A solução é deixar um recado na portaria: "quem perguntar pelo passaporte, mande para a recepção". A recepção é o casco do app, e lá dentro o roteador do Angular leva a pessoa à tela certa.

O que vai ao ar: a pasta do build

O npm run build transforma o projeto numa pasta de arquivos prontos: HTML, CSS, JavaScript e imagens. Não há Angular CLI, TypeScript nem Node.js nela. É um site estático: o servidor recebe um endereço, acha o arquivo e o entrega. Fazer o deploy é entregar essa pasta a um serviço que a coloque na internet.

Repare em três arquivos HTML na raiz. Desde a pré-renderização (), o index.html é a página da rota vazia, que só redireciona para /paises. O app sem nenhuma tela desenhada, o casco, é o index.csr.html. E o 404.html, uma cópia do casco, é a novidade deste capítulo.

O Render publica sites estáticos de graça, numa CDN: cópias da pasta em servidores pelo mundo, cada pessoa servida pelo mais perto. Ele se liga ao seu repositório no GitHub e, a cada push, roda o build e publica a pasta.

Por que /passaporte não tem arquivo

Quando você clica em "Meu passaporte", o roteador do Angular troca o endereço na barra e desenha a tela, sem pedir nada ao servidor. Mas digitar /passaporte na barra, recarregar a página ou abrir um link recebido por mensagem é um pedido novo ao servidor. E, para o servidor, /passaporte só existiria se houvesse um arquivo ou uma pasta com esse nome.

As páginas pré-renderizadas têm pasta: paises/JP/visao-geral/index.html responde por /paises/JP/visao-geral. As telas montadas no navegador (RenderMode.Client), não: o /passaporte, o /entrar e as abas de clima e de anotações. Para elas, o Render precisa de uma regra de rewrite: "a quem pedir /passaporte, entregue o /index.csr.html". O endereço na barra continua /passaporte, e o roteador desenha a tela.

A ordem das perguntas

Num site estático do Render, um pedido passa por estas perguntas, nesta ordem (conferido num site de verdade):

  1. Existe um arquivo com esse nome exato? Ele é entregue.
  2. Alguma regra vale para esse endereço? A regra decide.
  3. Existe uma pasta com esse nome e um index.html dentro? Ele é entregue.
  4. Existe um 404.html? Ele é entregue, com o status 404.
  5. Nada disso? Chega o texto Not Found.

O detalhe que pega muita gente está entre a segunda e a terceira pergunta: a regra vem antes da pasta. Uma regra que vale para todos os endereços (/*) passa por cima das páginas pré-renderizadas. Por isso o Passaporte tem regras só para as telas do navegador, e um 404.html para o resto.

O que muda na tela: abra o endereço do Render no celular. Navegue até a página de um país e recarregue: ela continua lá. Digite /passaporte na barra: a tela de entrar aparece, porque o guard pede login. Digite um país que não existe, como /paises/ZZ: aparece "Esta página não existe", do próprio app. Nesse caso, o console mostra Failed to load resource: the server responded with a status of 404 (), e é isso mesmo: o status 404 avisa navegadores e robôs de que a página não existe.

Com o HTTPS, o PWA do funciona fora do localhost: o navegador oferece instalar o Passaporte.

O Angular 22 pede o Node.js ^22.22.3 || ^24.15.0 || >=26.0.0. Num serviço novo, o Render usa por padrão o Node.js 24.22.1, que serve. Para fixar outra, a documentação do Render indica a variável NODE_VERSION ou um arquivo .node-version na raiz do repositório, com a versão numa linha.

Nos testes do livro, o Render mandou todos os arquivos com cache-control: public, max-age=0, s-maxage=300: o navegador confere a cada visita se o arquivo mudou, e a CDN guarda uma cópia por até 5 minutos. Um build novo limpa o cache da CDN. Uma regra nova, não: logo depois de mudar as regras, um endereço já pedido pode responder do jeito antigo por alguns minutos.

E fora do Render?

Todo serviço de site estático tem o seu jeito de escrever a regra. Nos exemplos da documentação de cada um, o destino é o index.html; no Passaporte, com a pré-renderização, troque pelo index.csr.html, como manda o guia de deploy do Angular. O livro testou só o Render: em outro serviço, confira como ele trata as pastas das páginas prontas.

Serviço Onde fica a regra O exemplo da documentação
Netlify arquivo _redirects /* /index.html 200
Vercel vercel.json "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
Firebase Hosting firebase.json "source": "**", "destination": "/index.html"
GitHub Pages não tem regras um 404.html com o casco do app (é assim que este livro é publicado)

Netlify, Vercel e Firebase entregam o arquivo que existe antes de aplicar a regra. O Angular também tem o ng deploy, que publica direto em alguns desses serviços depois de instalar o pacote de cada um.

Navegando pelo app, tudo funciona. Basta recarregar /passaporte, ou abrir esse endereço num link, para aparecer só o texto "Not Found", sem o app. O servidor procurou um arquivo, uma regra, uma pasta e um 404.html, e não achou nada. Como sair: uma regra de rewrite para cada tela montada no navegador, e o 404.html para o resto.

A regra /* → /index.html é a resposta clássica para uma SPA, e é a que aparece nos tutoriais. No Passaporte, ela dá um laço: o index.html só redireciona para /paises, e em /paises a mesma regra entrega o mesmo arquivo. A página fica recarregando; num teste com um servidor que segue a ordem do Render, foram 1817 pedidos em 8 segundos. Como sair: com pré-renderização, o casco é o index.csr.html.

Trocar o destino para /index.csr.html e manter o /* parece resolver: todas as telas abrem. Mas a regra vem antes da pasta. No teste do livro, uma pasta com o index.html da página Sobre, pedida sem a barra no fim, respondeu o casco, com o <app-root> vazio. O app funciona, porque o Angular desenha a tela no navegador, mas quem lê o HTML, como o robô do Google, perde tudo o que a pré-renderização () fez. Como sair: regras só para as telas do navegador. Confira com curl: /paises/JP/visao-geral tem de trazer o título "Japão · Passaporte".

O log diz "Your site is live", você abre o endereço, e a tela fica em branco: o console acusa 404 no main-….js. Aconteceu duas vezes nos testes do livro, logo depois do primeiro deploy de um site novo: arquivos que estavam na pasta publicada, páginas e scripts, respondiam "Not Found", e outros não. Minutos depois, tudo respondia. Como sair: espere um ou dois minutos e recarregue antes de procurar o erro no código.

E agora? O Passaporte está no ar, mas nada impede um push com um teste quebrado de chegar lá. No , o GitHub Actions roda os testes e o build a cada push, e o app só é publicado quando tudo passa.
