A aba Clima conhecia seis países, com um texto fixo. Neste capítulo, ela mostra o tempo de verdade, agora, na capital de qualquer um dos 195, buscado numa API de previsão do tempo. E o service perde o subscribe e o signal de status que ele mantinha à mão.

As duas mudanças usam a mesma ferramenta: o resource, um signal para dados que vêm de fora. Ao final do capítulo, você vai saber buscar dados com httpResource() e resource(), mostrar carregando, erro e resultado, e fazer a busca se repetir sozinha quando um signal muda.

No painel de chegadas, cada voo tem um status: "no horário", "atrasado", "pousou", "cancelado". Quem espera alguém não liga para a companhia a cada minuto: olha o painel, que se atualiza sozinho. E, se o voo mudar, o painel passa a mostrar o novo.

Um resource é uma linha desse painel. Ele sabe se está carregando, se deu certo ou se deu erro, e guarda o valor quando chega. E, se o que ele busca depende de um signal, como o país ou a unidade de temperatura, ele busca de novo sozinho quando o signal muda.

httpResource: uma requisição que vira signal

O httpResource() recebe uma função que devolve a URL, faz o GET com o HttpClient e guarda o resultado. Ele não precisa de subscribe, nem de signal de status: ele mesmo é o status.

Um resource tem vários signals:

SignalO que diz
status()'idle', 'loading', 'reloading', 'resolved', 'error' ou 'local'
isLoading()Se está buscando agora, pela primeira vez ou de novo
value()O valor; undefined enquanto não chega, e lança um erro se o status for 'error'
hasValue()Se há um valor que dá para ler sem susto
error()O erro, quando houver

Por isso o service sempre pergunta hasValue() antes de ler o value(). E, como no , ele expõe uma versão somente leitura, com asReadonly(): as telas olham o status, mas não escrevem. A lista usa esses signals direto no template:

Escrever no resource: o estado local

O set() e o update() de um resource trocam o valor na hora, sem requisição, e o status passa a 'local'. É o que o toggleVisited faz com o passaporte salvo: muda o valor no resource e, em seguida, manda o PUT. O PUT continua com o HttpClient e o subscribe, como no : o resource é para buscar; para salvar, uma ação.

Uma busca que depende de signals

A aba Clima pede o tempo à Open-Meteo, uma API gratuita e sem chave, com as coordenadas da capital:

  • A função lê dois signals, o país e a unidade. Quando um deles muda, o resource faz outra requisição; se a anterior ainda estiver a caminho, ela é cancelada, como o switchMap do .
  • Se a função devolver undefined, não há requisição, e o resource fica 'idle'.
  • No lugar de montar a URL à mão, um objeto com url e params: o Angular monta a parte do ?latitude=…&longitude=….

O httpResource() é o atalho para requisições. O resource() aceita qualquer carregamento que devolva uma Promise: um fetch, uma biblioteca de terceiros, um banco de dados no navegador. O params diz do que ele depende, e o loader carrega; o abortSignal avisa quando a busca foi cancelada.

Prefira o httpResource() quando for HTTP: ele passa pelo HttpClient, e funciona com os interceptors do e com o HttpTestingController dos testes.

O resource só pede os dados quando o Angular roda os efeitos, e só entrega a resposta depois que o app se estabiliza. Nos testes do Passaporte, a sequência é: TestBed.tick(), para a requisição sair; responder com o HttpTestingController; e esperar o whenStable():

Antes de a resposta chegar, o value() é undefined, e o TypeScript avisa. E, se a API falhar, ler o value() lança "Resource is currently in an error state". Como sair: confira com hasValue() antes de ler.

O resource é criado uma vez, num campo da classe, e se atualiza sozinho quando os signals que ele lê mudam. Como sair: em vez de criar outro, mude o signal de que ele depende, como o unit.

O resource refaz a requisição sempre que um signal que ele lê muda: para buscar, é ótimo; para salvar, é perigoso, e a documentação do Angular recomenda não usar assim. Como sair: buscar com resource; salvar com o HttpClient, quando a pessoa fizer algo.
