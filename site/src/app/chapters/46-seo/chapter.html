Peça /paises/JP ao Passaporte sem rodar JavaScript, como faz um robô de busca apressado ou o aplicativo de mensagens que monta a prévia de um link, e você recebe um <app-root> vazio e o título "Passaporte". Para quem procura, o Japão não existe. Neste capítulo, o build passa a gerar uma página de verdade para cada um dos 195 países, com título, descrição e cartão de compartilhamento próprios.

Ao final do capítulo, você vai saber por que uma SPA é quase invisível para buscadores, pré-renderizar páginas no build (SSG), dar a cada uma título, descrição e tags Open Graph, gerar o sitemap.xml e o robots.txt, e conferir tudo com a auditoria de SEO do Lighthouse.

Imagine duas lojas na mesma rua. A primeira tem a vitrine montada: quem passa vê o que há lá dentro, e o guia da cidade consegue listar o que ela vende. A segunda tem uma placa na porta, "entre para ver": lá dentro há tudo, mas o guia, que não entra em loja nenhuma, anota só a placa.

Uma SPA comum é a loja da placa: o HTML que chega é o <app-root> vazio, e o conteúdo só aparece depois que o JavaScript roda. Pré-renderizar é montar a vitrine: o build visita cada página e guarda o HTML pronto, que chega inteiro a quem pede.

Pré-renderizar no build

A pré-renderização (SSG, de static site generation) roda o app no build, uma vez para cada página, e guarda o HTML de cada uma. Ela precisa de dois pacotes do Angular e de três arquivos. O primeiro diz como cada rota sai:

  • RenderMode.Prerender: o build gera o HTML completo da rota. Vale para o que o Google deve achar.
  • Uma rota com parâmetro, como :code, precisa do getPrerenderParams, que diz quais valores gerar. O Passaporte pergunta à API dos países no build, e o build gera 195 páginas.
  • RenderMode.Client: a rota fica como numa SPA, montada no navegador. É o caso do passaporte e da tela de entrar, que dependem de quem entrou e não interessam ao Google.

No app.config.ts, o provideClientHydration liga a hidratação: o navegador aproveita o HTML que veio pronto, liga os eventos nele, e não desenha a página de novo. O withEventReplay() guarda os cliques que a pessoa der antes de o JavaScript chegar, e os repete depois.

Título, descrição e cartão de compartilhamento

O <title> de cada página já vinha do title das rotas, que você usou desde o . Quem escreve esse título é o TitleStrategy do roteador; o Passaporte troca o padrão por um seu, que escreve também a descrição e as tags Open Graph, as que os aplicativos de mensagem e as redes sociais leem para montar o cartão de um link:

  • O Title e o Meta são services do Angular que mexem no <head>; o updateTag cria a tag ou troca o conteúdo dela.
  • A descrição vem do data da rota mais funda; a das páginas fixas fica escrita na rota.
  • A descrição de cada país vem de um resolver, como o título do , que espera os países e monta a frase com a capital e a população.
  • O Open Graph pede endereços completos. O SITE_URL, em core/site.ts, ainda tem um endereço de exemplo: você o troca pelo seu quando publicar o app, no .

A pré-renderização gera as páginas uma vez, no build, e o resultado é um punhado de arquivos que qualquer hospedagem estática serve. Serve bem quando o conteúdo muda pouco, como a lista de países. Quando cada pedido precisa de uma página diferente, feita na hora, o Angular também sabe renderizar num servidor Node (o ng add @angular/ssr prepara isso, com um server.ts e o Express). Isso pede um servidor rodando o tempo todo, e fica para depois do livro.

Crie o main.server.ts, o app.config.server.ts e o app.routes.server.ts, e ponha o server e o outputMode no angular.json. No app.config.ts, acrescente o provideClientHydration(withEventReplay()).

Crie o core/site.ts e o core/seo-title-strategy.ts, e registre a estratégia no app.config.ts. Ponha o data: { description } nas rotas de países e do "Sobre", e o countryDescriptionResolver no resolve da página do país. No index.html, as tags fixas: og:type, og:site_name, og:locale e twitter:card.

Ponha em public/ uma imagem og.png de 1200 × 630 pixels, o tamanho que os cartões usam. Crie o scripts/sitemap.mjs, e troque o script build do package.json por ng build && node scripts/sitemap.mjs.

Rode npm run build. Abra o dist/passaporte/browser/paises/JP/visao-geral/index.html num editor de texto: o Japão está lá, no HTML. Sirva a pasta com um servidor estático e rode o Lighthouse.

O que muda na tela: nada, para quem usa o app. Mudam o título de cada aba, o código-fonte de cada página (Ctrl+U no navegador) e, depois de publicado, a prévia de um link do Passaporte num aplicativo de mensagens.

O build não tem como adivinhar quais países gerar. Como sair: o getPrerenderParams, ou RenderMode.Client para a rota.

No build, o app roda no Node.js, e não num navegador: não há localStorage, window nem document de verdade. O código que os usa direto, ao criar um componente, quebra a página inteira. Como sair: o que é do navegador vai para o afterNextRender (que só roda no navegador) ou para um try, como a cópia do passaporte faz desde o .

Sem o arquivo, o servidor fez o que faz com qualquer endereço desconhecido numa SPA: devolveu o index.csr.html. O robô leu HTML onde esperava as regras. Aconteceu com o build de desenvolvimento, que não roda o script do sitemap. Como sair: gerar o robots.txt em todo build que vai ao ar, e conferir com o Lighthouse antes de publicar.

E agora? O Passaporte tem vitrine. Antes de abri-lo ao mundo, ele ganha um último recurso: ser instalado como um aplicativo e abrir mesmo sem internet. No , ele vira um PWA.
