Até aqui, o passaporte morava no json-server, no seu computador: um passaporte só, de quem estivesse na frente da tela. Neste capítulo, ele vai para o Supabase. Cada conta ganha o próprio passaporte e o próprio diário de viagens, que agora dá para editar e apagar, e que acompanha a pessoa em qualquer navegador. E o banco garante que ninguém lê o passaporte de outra pessoa.

Ao final do capítulo, você vai saber criar tabelas no Supabase, proteger as linhas de cada pessoa com regras do banco, e fazer o CRUD completo pelo HttpClient: criar, ler, atualizar e apagar.

No cofre de um banco, as caixas de segurança ficam todas na mesma sala. O prédio é um só, mas cada cliente só abre a própria caixa, e a regra não depende da boa vontade de ninguém: a cada pedido, o funcionário confere o documento e só traz a caixa daquela pessoa. Dentro dela, o cliente faz quatro coisas: guarda, olha, troca e retira.

O Supabase é o prédio, e cada tabela é a sala das caixas. O token de quem entrou é o documento, e as regras por linha do banco são o funcionário que confere. Guardar, olhar, trocar e retirar são as quatro letras do CRUD. Um cofre sem a regra seria uma sala com as caixas destrancadas: a porta do prédio, a tela de entrar, não adiantaria nada.

As tabelas

O Supabase guarda os dados num banco PostgreSQL, em tabelas, como uma planilha com colunas fixas. O Passaporte usa duas: passports, com uma linha por conta (os países visitados e as anotações), e trips, com uma linha por viagem do diário. Elas nascem de um arquivo SQL, que você roda uma vez no SQL Editor do painel:

  • user_id … default auth.uid(): o auth.uid() é o id de quem fez o pedido, que o banco tira do token. O app nem manda essa coluna: o banco a preenche sozinho.
  • Os check repetem no banco as regras do formulário do : de 1 a 365 dias, transporte de uma lista, no máximo 40 letras. O formulário ajuda quem preenche; o banco garante, mesmo para quem não usa o formulário.
  • enable row level security liga as regras por linha (RLS). A partir daí, ninguém lê nem escreve linha nenhuma, a não ser que uma política deixe.
  • A política de trips vale para tudo (for all) e diz: uma linha é sua se o user_id dela é o seu auth.uid(). O using confere as linhas que já existem (para ler, mudar e apagar); o with check, as que você quer gravar.

A API REST que o Supabase monta

Você não escreve um servidor. Para cada tabela, o Supabase oferece uma API REST no endereço <projeto>/rest/v1/<tabela>, e cada letra do CRUD é um método HTTP:

Letra Requisição O que o banco faz
C (create)POST /rest/v1/tripsinsert
R (read)GET /rest/v1/trips?select=…&order=arrival.descselect … order by arrival desc
U (update)PATCH /rest/v1/trips?id=eq.7update … where id = 7
D (delete)DELETE /rest/v1/trips?id=eq.7delete … where id = 7

Os parâmetros dizem o resto: select escolhe as colunas, order ordena, e id=eq.7 é um filtro, "onde o id é igual a 7". Cada pedido leva dois cabeçalhos: o apikey, a chave publicável que diz de qual projeto é o pedido, e o Authorization, com o token de quem pede. É aqui que o interceptor do passa a valer de verdade: o API_URL agora aponta para o Supabase, e o interceptor põe os dois.

O Passport fala com o Supabase

O service muda por dentro, e as telas quase não percebem. O arquivo inteiro, com as linhas novas destacadas:

  • R: os dois httpResource devolvem undefined quando ninguém entrou. Você viu no : sem requisição, o resource fica 'idle'. Quando a pessoa entra ou sai, o signedIn() muda, e o resource pede de novo, sozinho.
  • A API sempre devolve uma lista, mesmo quando só pode haver uma linha. O parse do httpResource transforma a lista na linha de quem entrou, ou em null, se a pessoa ainda não salvou nada.
  • C: o POST leva o cabeçalho Prefer: return=representation, que pede ao Supabase a linha criada, já com o id que o banco deu. Sem o id, não daria para editar nem apagar a viagem depois.
  • U: o PATCH leva o id no filtro (id=eq.7) e só as mudanças no corpo. O id é da linha, e não pode mudar.
  • D: o DELETE também leva o filtro. Sem ele, o Supabase recusa: apagar a tabela inteira por engano não dá.
  • O passaporte é salvo com um upsert: um POST com Prefer: resolution=merge-duplicates cria a linha na primeira vez e a atualiza nas seguintes.
  • O firstValueFrom, do RxJS, transforma o Observable do HttpClient numa Promise da primeira resposta. Assim, quem chama pode usar await, e o erro vira uma exceção, que se trata com try/catch.

A cópia do localStorage, do , continua: se o Supabase não responder, o app mostra a última versão conhecida. Mas agora a chave tem o id de quem entrou (passaporte:<id>), e sem login não há cópia. Num computador compartilhado, a próxima pessoa não vê o passaporte de quem usou antes.

O que muda na tela: entre na sua conta, marque países e registre uma viagem. Abra o Table Editor no painel: as linhas estão lá, com o seu user_id. Edite a viagem e apague-a, e veja a tabela acompanhar. Agora crie uma segunda conta e entre com ela: o passaporte começa vazio, e o da primeira conta continua intacto. Por fim, saia: sem login, você ainda marca países, mas só nesta visita.

Com o RLS ligado e sem política, o banco não deixa nada. Na escrita, ao menos há um erro. Na leitura, não: a resposta é 200 com uma lista vazia, e o app mostra "Nenhuma viagem registrada ainda", como se tudo estivesse certo. Como sair: criar as políticas junto com a tabela, como no passaporte.sql.

A chave publicável vai no código do app, e qualquer um a encontra no navegador. Sem o RLS, ela basta para ler, mudar e apagar as linhas de todo mundo, como o simulador mostra. O guard do capítulo 38 não protege nada aqui: ninguém precisa passar pela tela. Como sair: enable row level security em toda tabela que o app usa.

Sem o Prefer: return=representation, o Supabase cria a linha e responde 201 com o corpo vazio. O HttpClient entrega null, e desestruturar null quebra. O pior: a viagem foi salva, mas o formulário diz que não, e quem clica de novo cria uma segunda. Como sair: pedir a linha criada com o cabeçalho.

Um POST comum só cria. O primeiro país marcado cria a linha do passaporte (201); o segundo tenta criar outra com o mesmo user_id e leva um 409 Conflict. Como sair: Prefer: resolution=merge-duplicates, que transforma o POST em "cria ou atualiza".

A viagem que vem do formulário tem o id, e mandá-la inteira no corpo é pedir para mudar o id também. A coluna é generated always: o banco recusa com 400. Como sair: separar o id das mudanças, com const { id, ...changes } = trip, e usar o id só no filtro.

E agora? Os dados chegam do Supabase, mas a tela abre antes deles: por um instante, o passaporte aparece vazio. No , um resolver carrega os dados antes de a tela abrir, e você compara essa escolha com a de buscar os dados dentro do componente.
