Até aqui, um push com um teste quebrado ia direto para o ar. Agora, a cada push, o GitHub baixa o Passaporte numa máquina limpa, roda os testes e o build, e marca o commit com ✓ ou ✗. O Render só publica os commits com ✓.

Esses dois commits são do repositório deste livro. O de baixo quebrou um teste e nunca chegou ao Render; o de cima corrigiu e foi publicado sozinho. Ao final, você vai saber escrever um workflow do GitHub Actions, ler o que ele diz quando algo falha e fazer o Render esperar por ele.

Antes de cada voo, o avião passa pela mesma revisão: combustível, pneus, instrumentos. Ninguém pula etapas porque "ontem estava tudo bem". E, se um item falha, o avião fica no chão; os passageiros esperam o voo seguinte, mas ninguém decola com um problema conhecido.

O GitHub Actions é essa revisão, feita a cada push, sempre do mesmo jeito. O Render é a torre de controle: só libera a decolagem quando a revisão termina sem nenhum item vermelho. Se algo falhou, a versão que já está no ar continua voando.

Integração contínua

Rodar os testes antes de cada push depende de lembrar. A integração contínua (CI) tira a memória da conta: uma máquina confere cada mudança assim que ela chega ao repositório. No GitHub, quem faz isso é o GitHub Actions, gratuito nos repositórios públicos.

O que fazer, e quando, fica num workflow: um arquivo YAML na pasta .github/workflows do repositório. O do Passaporte:

  • on diz quando rodar: a cada push na main e a cada pull request. No YAML, a indentação é a estrutura: branches está dentro de push, que está dentro de on.
  • jobs lista os trabalhos. O Passaporte tem um, o test-and-build, com o nome "Testes e build", que é o nome do check que aparece no GitHub.
  • runs-on: ubuntu-latest escolhe o runner: uma máquina Linux nova, emprestada pelo GitHub para essa execução e descartada no fim. Ela não tem nada da sua máquina: nem o node_modules, nem arquivos que você esqueceu de commitar.
  • steps são os passos, em ordem. Os que têm uses rodam uma action pronta: actions/checkout baixa o repositório, e actions/setup-node instala o Node.js 24 (e, como o package.json tem "packageManager": "npm@…", guarda o cache do npm sozinho). Os que têm run rodam um comando, como no seu terminal.

Se um passo falha, o job para ali: os passos seguintes nem rodam, e o check fica vermelho. O npm test não fica esperando mudanças como na sua máquina: o GitHub Actions define a variável CI, e o Angular roda os testes uma vez só.

O Render espera o CI

No Render, o Auto-Deploy tem três opções: On Commit (o padrão), que publica assim que recebe o push; After CI Checks Pass, que espera todos os checks do commit; e Off. Com a segunda, o CI vira o porteiro do deploy. No render.yaml, é uma linha:

Crie a pasta .github/workflows na raiz do projeto (o ponto no começo do nome faz parte dele) e, dentro dela, o ci.yml da seção anterior. Faça o commit e o push.

No GitHub, abra a aba Actions do repositório: a execução aparece com o nome do commit. Clique nela e no job "Testes e build" para ver cada passo. No Passaporte do livro, a execução inteira levou menos de 30 segundos:

No Render, abra o site, vá a Settings e, em Auto-Deploy, escolha After CI Checks Pass. Se você criou o site pelo Blueprint, ponha o autoDeployTrigger: checksPass no render.yaml.

O Render precisa enxergar os checks do GitHub: ele tem de estar ligado ao repositório pelo app do Render no GitHub, como acontece quando você escolhe o repositório pelo painel.

Desfaça a mudança e faça outro push na mesma branch: o check fica verde. Faça o merge, e o Render publica a main sozinho, logo depois que o CI da main termina.

O "After CI Checks Pass" protege o site, mas a main ainda aceita um merge com o check vermelho. Para barrar isso também, o GitHub tem as regras de proteção de branch, com a opção Require status checks to pass before merging: com ela, o botão de merge só libera depois que o check escolhido ("Testes e build") passar.

Outro caminho para publicar é o Deploy Hook do Render: uma URL secreta (Settings → Deploy Hook) que dispara um deploy quando recebe um pedido. O workflow guarda a URL como secret do repositório e a chama num último passo, depois dos testes. O livro ficou com o "After CI Checks Pass" porque não tem segredo nenhum para guardar.

Você instalou um pacote, o app rodou, e o commit levou só o package.json. Na sua máquina, o node_modules já tinha tudo; o runner começa do zero, e o npm ci se recusa a instalar com um lock que não bate. O job para no segundo passo, e os testes nem rodam. Como sair: rode npm install e mande o package-lock.json no mesmo commit do package.json.

O node-version ficou na mesma coluna do with, e não dentro dele. Para o YAML, o with ficou vazio e o node-version virou uma chave solta do passo. O GitHub nem chega a criar o job: a execução falha na hora, com a linha e a coluna de cada problema. Como sair: conte os espaços; o que fica dentro de uma chave vai dois espaços mais à direita, e a anotação diz a linha onde olhar.

Com "After CI Checks Pass", o Render só publica um commit que tem checks, e todos verdes. Nos testes do livro, um commit com [skip ci] na mensagem (que faz o GitHub não rodar o workflow) ficou sem nenhum check, e o Render não fez nada: nem deploy, nem evento. O mesmo acontece se o workflow não roda para aquela branch (um on só com pull_request, por exemplo), ou se o Render não está ligado ao repositório pelo app do GitHub: no livro, antes de o app ter acesso ao repositório, nenhum push chegava ao Render. Como sair: confira na lista de commits se o último tem ✓; sem marca nenhuma, o Render não vai publicar. O workflow precisa rodar no push da branch que o Render publica.
