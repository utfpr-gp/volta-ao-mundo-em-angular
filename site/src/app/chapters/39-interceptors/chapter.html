O Passaporte sabe quem entrou, mas o servidor ainda não sabe: as requisições saem sem dizer quem as fez. Neste capítulo, toda requisição para a API do Passaporte passa a levar o token de quem entrou, sem que nenhum service precise lembrar disso. De quebra, o app ganha uma barra de carregamento e passa a saber, num lugar só, quando a API não respondeu.

Ao final do capítulo, você vai saber escrever um interceptor, registrá-lo no HttpClient, mexer na requisição na ida e na resposta na volta, e escolher para quais endereços o token vai.

Numa empresa grande, ninguém leva a própria carta até o correio: deixa na sala de expedição. Lá, toda carta passa pelas mesmas mesas, sempre na mesma ordem. A primeira anota no livro que uma carta saiu. A segunda põe o selo da empresa, mas só nas cartas para a matriz: carta para outra empresa não leva o selo interno. Quando a resposta chega, ela atravessa as mesmas mesas, de trás para a frente: se veio uma devolução, alguém avisa o andar inteiro; e o livro anota que a carta voltou.

Quem escreveu a carta não precisa lembrar de nada disso. Os interceptors são as mesas da expedição do HttpClient: toda requisição passa por eles na ida, e toda resposta, na volta.

Uma função no meio do caminho

Um interceptor é uma função do tipo HttpInterceptorFn. Ela recebe a requisição (req) e o próximo passo do caminho (next), e devolve o Observable da resposta. O mais simples dos três do Passaporte conta as requisições a caminho:

  • O que vem antes do next(req) acontece na ida: o start() soma uma requisição ao contador do service Loading.
  • next(req) entrega a requisição ao próximo interceptor, ou, se ele for o último, à rede. O que ele devolve é a resposta que ainda vai chegar.
  • Os operadores no pipe acontecem na volta. O finalize roda quando a requisição termina, de qualquer jeito: com resposta, com erro ou cancelada. É ali que o stop() desconta.
  • Como o guard do , o interceptor pode usar o inject(): o Angular o chama num contexto de injeção.

O token, só para a API do Passaporte

O token de acesso, o JWT que você conheceu no , vai num cabeçalho HTTP chamado Authorization, no formato Bearer <token>. O Auth ganhou um computed que o lê da sessão:

E o interceptor o põe em toda requisição para a API do Passaporte:

  • O isApiRequest, em core/api.ts, confere se o endereço começa com o da API do Passaporte. A API de países e o Open-Meteo são de outras pessoas: o token de quem entrou não é da conta delas.
  • A requisição é imutável: ninguém a altera depois de criada. Para mudar alguma coisa, o req.clone(…) faz uma cópia com a mudança, e o setHeaders acrescenta o cabeçalho.
  • O from(auth.whenReady()) transforma a Promise do capítulo 38 num Observable, e o switchMap, que você viu no , só solta a requisição quando ela se resolve. Sem essa espera, o primeiro pedido do app sai antes de a sessão ser lida, e sem token (está nas armadilhas).

Os erros num lugar só

Até aqui, o Passport cuidava dos próprios erros: um signal para o GET que falhou, outro para o PUT. Com um interceptor, toda falha da API passa por um lugar só:

  • O tap olha cada evento que volta, sem mudar nada. Quando chega a resposta (HttpEventType.Response), a API está de pé, e o aviso some.
  • O catchError acende o aviso e devolve o mesmo erro com throwError. O interceptor avisa o app, mas quem fez a requisição continua sabendo que ela falhou.
  • O aviso mora no service ApiStatus, e o app.html o lê. O Passport ficou mais curto: perdeu o putFailed e o saveFailed.

Abra a aba Rede do navegador depois de entrar: antes de cada requisição com o token para o json-server, aparece uma do tipo OPTIONS. É o preflight. Um cabeçalho como o Authorization, numa requisição para outro endereço, faz o navegador perguntar antes ao servidor: "você aceita este cabeçalho, vindo de localhost:4200?". O json-server responde que sim (204), e a requisição de verdade sai. Um servidor que não responde à pergunta bloqueia a requisição, e é por isso que o token não pode ir para qualquer endereço.

Os interceptors só veem as requisições do HttpClient. O @supabase/supabase-js usa o fetch do navegador direto, por fora dele: o login, o logout e a renovação do token não passam pelo authInterceptor, nem acendem a barra de carregamento. E nem precisam: o cliente do Supabase põe o próprio token nas requisições que faz.

Em tutoriais mais antigos, o interceptor é uma classe que implementa HttpInterceptor, com o método intercept, registrada no token HTTP_INTERCEPTORS. Ainda funciona, com withInterceptorsFromDi(), mas a própria documentação do Angular recomenda as funções e avisa que o suporte às classes pode ser retirado numa versão futura.

O que muda na tela: recarregue a página e veja a barra dourada correr sob o cabeçalho enquanto os países chegam. Entre na sua conta, abra a aba Rede do navegador (F12) e marque um país: o PUT para localhost:3000 leva o cabeçalho Authorization, e o GET do paises.json, não. Por fim, pare o npm run api e marque outro país: o aviso amarelo aparece, e a barra some mesmo com o erro.

O json-server não confere o token: ele aceita qualquer pedido. Quem vai conferir é o Supabase, quando os dados do passaporte forem para lá.

Como sair: esperar a sessão, com from(auth.whenReady()) e switchMap, antes de ler o token. É a mesma pressa do guard que decidia antes da hora, no capítulo 38.

Sem conferir o endereço, o token vai também para a API de países. O cabeçalho Authorization faz o navegador mandar antes o OPTIONS do preflight; o GitHub Pages, que hospeda a API, responde 405, e o navegador bloqueia a requisição. A lista mostra "Não foi possível carregar os países", mas só para quem entrou: sem login, não há token, e tudo funciona. Um erro que depende de quem usa o app é dos mais difíceis de achar.

O Open-Meteo, ao contrário, aceita o cabeçalho, e aí o problema é pior porque não aparece: o seu token vai parar no servidor de outra pessoa. Como sair: pôr o token só nas requisições para a sua API, com o isApiRequest.

A requisição e os cabeçalhos são imutáveis. A tentativa 1 nem compila. A tentativa 2 compila, e é pior: o set devolve uma cópia dos cabeçalhos com o token, que ninguém usa, e a requisição sai como estava, sem erro nenhum. Como sair: next(req.clone({ setHeaders: { Authorization: … } })).

Devolver EMPTY no catchError transforma o erro num "terminou sem nada". Quem fez o subscribe não recebe nem o valor nem o erro, só o fim, e acha que deu certo. O httpResource vai para o estado de erro com o NG0991, e o erro de rede verdadeiro, que explicaria o problema, some. Como sair: o interceptor avisa o que precisa e devolve o mesmo erro, com throwError(() => error).

Com o tap, o stop() só roda quando chega uma resposta. Uma requisição que dá erro nunca chega lá, e uma cancelada também não (o switchMap das anotações cancela o PUT anterior a cada letra). O contador nunca volta a zero. Como sair: finalize, que roda em qualquer fim.

E agora? Cada requisição para a API já diz quem a fez, mas a API do Passaporte ainda é o json-server, que não confere nada. No , os dados do passaporte vão para o Supabase, que confere o token em cada pedido e só entrega a cada pessoa o que é dela.
